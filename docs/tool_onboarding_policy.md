# 工具能力登记与扩展策略

更新日期：2026-07-24

## 背景

当前 Argus 原型内置四个工具：`run_shell`、`read_file`、`write_file`、`web_fetch`。这足以覆盖课程验收中的代码执行、文件访问、网页读取和不可信来源传播，但真实 Agent 往往会接入数据库、邮件、浏览器、向量库、HTTP 发送、云存储等更多工具。

如果只使用固定白名单，新工具会被阻断，安全但不够灵活；如果直接放开新工具，又会引入工具调用劫持和数据外联风险。因此本项目把“工具集超出预设怎么办”拆成两层：

- 当前已实现的小工程补丁：工具能力注册表。
- 后续需要继续做的完整方向：工具能力标签、最小权限、场景策略和旁路观察。

## 当前实现

代码入口：

- `src/guardian/tool_registry.py`
- `src/guardian/policy.py`
- `tests/test_tool_registry.py`

`tool_registry.py` 为每个内置工具记录：

- `name`：工具名。
- `capabilities`：能力标签，例如 `code_execution`、`filesystem_read`、`network_read`。
- `risk`：工具风险等级，例如 `critical`、`high`、`medium`。
- `audit_focus`：审计重点，例如危险命令、敏感文件读取、记忆中毒、远程载荷。
- `enabled`：是否进入当前允许集合。

`PolicyLayer` 仍然坚持“未知工具默认阻断”。区别是，阻断理由现在会明确提示新工具应先登记能力标签、最小权限和审计关注点，而不是只说“不在白名单”。这样演示时可以解释：项目没有把未知工具无条件放行，而是把新工具接入变成一个可治理流程。

## 新工具接入建议

1. 先在旁路观察模式记录真实请求，不让新工具直接执行高风险动作。
2. 在 `TOOL_PROFILES` 中登记工具能力，例如 `database_write`、`network_send`、`browser_control`。
3. 为该工具补充最小权限边界，例如只读、只写沙箱目录、只访问指定域名。
4. 在 `PolicyLayer` 中补充针对该能力的确定性规则。
5. 在 `TaintLayer` 中判断该工具是污点来源还是高权限 sink。
6. 在 `AnomalyLayer` 中补充与该工具相关的异常链路，例如 `read_file -> send_http`。
7. 加入良性样本和攻击样本，运行 `scripts/run_benchmark.py` 验证误报与漏报。

## 本阶段结论

“工具不足”本身不是一个简单小问题，因为完整泛化要处理不同工具的权限、参数、业务语境和外部环境。但本阶段已经补上了工具能力注册入口和测试，使后续扩展不再依赖散落常量。课程定稿中可以把它表述为：当前原型对内置工具可验收，对新工具采用默认阻断与能力登记策略；大规模开放工具集的自动化治理作为后续展望。
